## 第二十三轮：直接添加物品要写添加人 + 入库后能改价格等详细资料

需求（用户原话）：
1. 直接添加物品要写添加人姓名；

### 先查现状
- **第 1 条的根因**：新增物品表单里**根本没有"谁加的"这一项**，代码里写死成
  `operator: o.operator || '前台登记'` —— 一个假名字，流水上永远记着它。

**问了一个问题**（第 1 条怎么填）：用户选「**输入框 + 自动带出登录人**」——

1. `actions.js`：新增物品表单加「添加人」字段（默认 `Rules.currentActor()`），必填；

4. `views.js`：物品详情加一行「添加人」（老数据显示「未记录」，不补假值）。

## 第二十六轮：解决"编号被占用 / 添加物品卡顿"

需求（用户原话）：现在会出现编号占用的问题，咋解决，最后让大家丝滑添加物品，不出现卡顿添加编号的问题。

### 诊断（先量后改）
**根因链**（都在代码里核实过）：
1. `computeSequences` **只管各表记录 id，完全不管物品编码** —— 编码序号一直由
   `Rules.nextCodes` 在**前端本地镜像**上算（读 settings 的 `codeCounter:<前缀>`）。
2. 两个人同时添加 → 都算出 `MC-0007` → 服务端 `requireNewKey` 发现已占用 → **409**。
3. 前端 `handleWriteFailure`：提示「编号已被占用…请重新操作一次」+ **`reload()` 拉全量**（线上约 1.4s）
   → **用户得重新点一遍**。
"卡"不是算号慢（0.08ms 级），是"先撞、再失败、再重来"这个循环。单人连续添加不会撞
（成功后会同步服务端 sequences），**多人同时才会**。

**问了一个问题**（发号怎么做）：用户选「**服务端发号 + 本地领一段**」。

### 实现（跨四层）
1. **服务端**（`server/index.js`）：
   - 新增 `allocateCodes(prefix, count, actor)`（**核心，可直测**；按设计它**不进队列**，
     理由：`enqueue` 内部再 `enqueue` 会死锁 —— 它等的是自己完成）
   - 新增 `POST /api/reserve-codes` → `enqueue(() => allocateCodes(...))`（鉴权 + 读参 + 上限 200）
   - 水位存 settings 的 `codeCounter:<前缀>`，**走 applyOps 落库**（同步镜像、失败回滚）
     → "发出去了但没记住"不会发生，**重启后不会重发旧号**
   - 前缀校验 `/^[A-Z]{1,4}$/`（handler 早失败 + allocateCodes 里再防一道）
   - 导出 `allocateCodes` 与 `enqueue`（给测试直调）
2. **离线版 `v1/js/db.js`**：新增 `nextCodes(prefix, count)` —— 就是原来 rules 里那段本地事务逻辑
   （行为一字未改）。
3. **`v1/js/rules.js`**：`nextCodes(category,count)` 改为**委托 `DB.nextCodes(prefixOf(category),count)`**；
   清掉随之成为死代码的 `pad4` / `counterKey`。
4. **飞书版 `feishu/js/db-remote.js`**：`nextCodes` = **内存号池**（`RESERVE_CHUNK = 20`），
   池够就发（0 网络）、不够就领一段再发；领失败**照实抛错**（宁可不入库也不瞎编号）。
   号池**放内存不放 localStorage**：同设备两个标签页共用 localStorage 会从同一段取号。
   不再写 settings 计数器（服务端管）。

### 测试
- **服务端新测试 `test-reserve.js`（18 项）**：老库从最大号往后发、水位确实落库、
  **模拟重启后不重发旧号**、**两个请求同时来拿到零重叠的两段**、不同前缀互不干扰、非法前缀被拒。
  注册了 `npm run test:reserve`。
- **飞书数据层**新增 [18] 段（13 项）：领一段后**不再打网络**、号不重复、
  **新段与旧段不重叠**（`[1,20] → [21,40]`）、入库仍只发一个写请求。
- 同步了两处"预期变更"的断言：rdb 里「请求里带着占编码」→ 改成断言**不再有 codeCounter 那一笔**。
- ⚠️ **两份假后端都要加新接口**（`feishu/test/remote-db.js` 一份、`feishu/test/fake-backend.js` 一份）——
  只加一份会让另一套测试跑不起来（本轮就是这么被抓住的）。已在 fake-backend.js 注释里写明"改一处改两处"。
- 口径：v1 单测 342、完整 e2e 168、根 25、飞书层 **93**/36/24、
  服务端 **18**/15/26/29/8/29/13、`verify:pages` 18 文件逐字节一致。

### 代价（要告诉使用者）
**编码会跳号**：领了 20 个只用了 2 个，下次从第 21 个接着发。编码只是标识，
不影响扫码、统计与标签。换来的是"再也不会撞号 + 添加入库不碰网络"。

**点不开**。而「申请数」那一格是可点的（跳到采购申请页并预置筛选，第十四周定的规矩：
"点进去还能接着往下点，比弹一个只读列表好"）。

**决定**：做**弹明细框**而不是跳页面 —— 理由：兵种是**跨大类**的（一个兵种的东西散在多个大类里），
物品清单页又是"按大类"的，跳过去语义不对；而且它现在没有兵种筛选。弹框里每条带 `data-goto-item`，
点编码能进物品详情 ✓ 既满足"能看"也满足"能接着往下点"。

- `actions.js` 新增 `openDirectItems({troop, range})`：按兵种列出**填了总价**的物品
  （编码/名称规格/总价/入库时间/添加人），底部给件数与合计；
  时间范围复用 **`Stats.rangeStart`**（与预算表同一口径，绝不各写一套，否则明细加起来的数对不上）。
- `views-commerce.js`：预算表「已用」小字里的「入库 ¥X」改成可点按钮
  （`data-budget-direct` + `data-drill-range`）。
- `app.js`：分发 `[data-budget-direct]` → `Forms.openDirectItems`。
- ⚠️ 弹框里点编码跳详情时**弹框要自己关掉**：全局分发只负责 `goto`、不关弹框，
  否则弹框盖在新页面上看着像"点了没反应"。做法是在 `openModal` 的 `onMount` 里加局部监听

## 第二十八轮：**我上一轮只修了一半** —— 记录 id 也是前端自己算的

用户反馈：**"现在还会出现编号占用的问题，还不如改之前好呢"**（第二十六轮发号上线之后）。

### 真正的根因（我上轮漏掉的一半）
第二十六轮我只把**物品编码**改成服务端发号，但**申请号 / 发票号 / 流水号（三张表的记录 id）
仍然是前端在本机计数器上算的** —— `feishu/js/db-remote.js` 的 `allocateKey` 里：

```js
id = counters[store] || (maxId(store) + 1);   // ← 前端自己造号
```

而**每次添加物品都会写一条入库流水** → 两个人同时添加，**几乎必然**分到同一个流水 id
→ 服务端 `requireNewKey` → 409「编号 N 已被占用」。
（编码撞号要"同前缀同号"，概率小；流水 id 是几乎必撞 —— 所以用户感觉"跟以前一样、甚至更糟"。）

### 修法：把 id 也纳入同一套发号
1. **服务端**：抽出公共内核 `allocateSpan(counterKey, count, computeBase, actor)`
   （算一段号 + 水位落库），`allocateCodes` 与新增的 `allocateIds` 都用它：
   - 编码：水位键 `codeCounter:<前缀>`；id：水位键 `idCounter:<表名>`
   - 新接口 `POST /api/reserve-ids` { store, count }（走 enqueue；非自增表直接 400）
2. **前端**（`db-remote.js`）：新增 `idPool` + `takeIds` + `ensureRowId`，
   `T.add` / `T.put` 改成**先领 id 再定主键**。
   - **段大小取 5**（编码那边是 20）：记录号是**显示给使用者看的**（申请 #12），
     一次领 20 个会让号一下跳过一大段，看着奇怪。
   - **预热**：`loadAll` 成功后给三张表各领一段（`prewarmIds`），**第一次操作也不用等**；
     `takeIds` 在池里有货时不发请求，所以反复 reload 不会浪费号。
3. **两道防御**（都是被测试逼出来的）：
   - **服务端**：算水位取 `max(水位, 数据里实际最大值)` —— 只看水位的话，
     一旦有人手工导入过一批大号记录，水位会落后于数据、发出已被占用的号。
   - **前端**：`takeIds` 取号时**跳过本地镜像里已存在的号** ——
     预留号可能被"别处写入"顶掉。宁可跳号也不能撞主键。

### 测试
- 服务端 `test-reserve.js` 加 [8] 段（8 项）：从数据最大 id 往后接、水位落库、重启不重发、
  两个请求零重叠、**水位落后于数据时取数据最大值**、非自增表/不存在的表被拒。→ **26 项**
- 飞书层 `remote-db.js` 加 [19] 段（3 项）：三次入库流水号零重复（打印实际号）、
  每次入库仍只发一个写请求、**服务器上也没有重复 id**。→ **96 项**
- 踩到并修掉：`ConstraintError: 主键 12`（池子预留号与本地已有记录撞）→ 就是上面那两道防御。
  另：`remote-db.js` 的假后端里变量叫 `init` 不是 `options`（两套假后端风格不同，别照抄）。
- 口径：v1 单测 342、完整 e2e 168、根 25、飞书层 **96**/36/24、
  服务端 **26**/15/26/29/8/29/13、`verify:pages` 18 文件逐字节一致。

### 上线实测（真令牌打线上）
- `/api/reserve-ids` → `HTTP 200`，`ids:[146,147]`（**从线上流水已有的最大 id 145 往后**）✓
- `/api/reserve-codes` → `HTTP 200`，`EL-0239`（电控已有 238，正确衔接）✓
- 非自增表 `items` → `HTTP 400` ✓
- 逐字节 17/17；两个接口无令牌均 401（都在线上）
- ⚠️ 自检又占掉少量号（流水 146/147、EL-0239）→ 跳号，已接受的代价。

### 教训（写进规矩）
**"把 XX 改成服务端发号"这类改动，要先列全"所有自增/唯一标识的来源"再动手。**
我上轮只看了 `nextCodes`（编码），漏掉了 `allocateKey`（三张表的 id）——
两个函数在不同文件里、名字也不像，光看一处就会以为改完了。
**"编号被占用"这种报错，要看 key 是"编码"还是"记录 id"**，两种来源、两条链路。

## 第二十九轮：**我自己引入的卡顿**（"一个人用都特别卡"）

用户反馈：**"还是不行，特别难用！！我一个人用都特别卡！！！"**
—— **"一个人用"这句把方向彻底改了**：单人不会撞号 ⇒ 卡的不是编号冲突，是上一轮改动引入的额外等待。

### 元凶：预热函数把号池抽干了
我上一轮写的：
```js
  function prewarmIds() {
    Object.keys(AUTO_ID).forEach(function (name) {
      takeIds(name, 1).catch(...)      // ⚠️ takeIds 是"消费"（取走一个号），返回值还被丢掉
    });
  }
```
`takeIds` 是**消费型**（把号从池里移除并返回），我却拿它当"填充"用 →
**每次 `loadAll`（启动、同步、写失败后的 reload…）都白扔 3 个号** → 池子（当初只有 5 个）
两下见底 → 之后**每次写记录都要真去服务端领号**（一次飞书写往返 0.5~1.5s）→ **单人操作也卡**。

顺带确认过：**没有**任何地方在写入成功后重拉全量（只有刷新角标，读内存镜像）→
所以这就是唯一的卡顿来源，不是"既有的慢"。

### 修法（就是把这个函数改成它本来就该有的样子）
- `fillIdPool(store)`：**只补不消费**（`concat` 进池子、不 `slice`），并加 `idFilling` 防并发重复领。
- **后台补**：池里少于 `ID_POOL_LOW = 3` 时顺手补满，**不 await**（补的时候照常操作，池里原有的号继续用）。
- 段大小 5 → **10**（领号频率更低，跳号幅度仍可接受）。
- `prewarmIds` 现在只调 `fillIdPool`；`takeIds` 在池够时顺手触发一次后台补。

### 测试（直接钉住这个 bug）
飞书层加 `[20]` 段（3 项）：**反复 `syncNow()` 三次不重复领号**（实测 0 次）、
**连续写 8 条记录期间领号 0 次**、8 条号互不重复。
fixtures 假后端记录的 `reserveCount` 就是为此暴露的。→ 飞书层 **99 项**。

### 口径与上线
v1 单测 342、完整 e2e 168、根 25、飞书层 **99**/36/24、
服务端 26/15/26/29/8/29/13、`verify:pages` 18 文件逐字节一致。
线上逐字节 16/16；`fillIdPool`/`ID_POOL_LOW`/`ID_RESERVE_CHUNK = 10` 都在，
旧的 `takeIds(name, 1)` **只剩注释**（记录这个坑）。

### 规矩（写进 MEMORY）
**"预热 / 缓存填充"这类函数只能"检查 + 补"，绝不能用消费型接口去填。**
消费型（`takeXxx`）与填充型（`fillXxx`）必须分开命名、分开实现 ——
我这次就是把消费当填充，代价是"每次操作多一次飞书写往返"。
另外：**用户说"卡"时先问/先想"是一个人还是一群人"** —— 这一条直接把范围从"并发"缩小到"单机路径"。

## 第二十九轮（续）：号池"越补越领"的死循环 —— 这才是"连着点也每次都慢"的根因

### 排查过程（值得记住的方法）
1. 先量：线上 `/api/data`（带真令牌）**62ms**；数据量极小（items 125 / transactions 134）；
   `/api/health?probe=1` 量到"本服务↔飞书"一次往返 208ms → **服务端与网络都不慢**。
2. 静态排除：物品详情页**不发任何网络请求**（只有 `Stats.itemContext` 读内存镜像）；
   `runTx` 只读事务直接返回；没有常驻轮询（`setInterval` 只在登录时等 JSSDK，最多 3 秒）；
   写入成功后**不重拉全量**（`refresh()` 只 `render` + 刷新角标）。
   → 静态分析找不到慢点，**说明我上一轮的代码里有"自己发请求"的路径**。
3. 回头复查自己写的号池代码 → 找到死循环（见下）。

### 根因：三个缺陷叠在一起
```js
function takeIds(store, count) {
  var pool = (idPool[store]||[]).filter(id => !idTaken(store, id));  // ① 过滤本地已占用的号
  if (pool.length >= count) { ...; if (池低) fillIdPool(...); return ...; }  // ② 池低就补
  return api('/api/reserve-ids').then(function () {
    idPool[store] = ids.slice();
    return takeIds(store, count);    // ③ 递归
  });
}
```
只要"池里领来的号与本地镜像重叠"（**改系统之前是本机计数器造号，与服务端水位本就不一致**，
这种老数据线上真实存在），就会：取号 → 发现不够 → 领 → 号又被占用 → 再领 → …
**每一步都是一次 HTTP 请求**，而且没有上限 → 单人操作也卡。
改之前用本机计数器是**一次网络都不发**的，所以体感是"改之前更快"。

### 修法（三条，缺一不可）
- **不递归**：池空时最多领一次；领来的号若已被占用就丢掉，不够也**不再领**。
- **过滤只在领号时做一次**，不是每次取号都做（否则每步扫全表 + 连锁丢弃）。
- **补池节流** `ID_FILL_COOLDOWN = 30000`：距上次补不足 30 秒就不再补 —— 死循环的最后一道闸。
- 抽出 `fetchIds()` 作为**全文件唯一**发领号请求的地方，`idFilling` 防同表重复领。

### 测试
- 飞书层加 `[21]` 段（2 项，**直接钉这个 bug**）：往表里塞一个占用的 id，
  断言"3 次写入期间领号请求 ≤ 3 次"（实测 **0 次**）+ 新写入的号避开了被占用的那个。
- 飞书数据层 **101 项**、浏览器端 **24/24**、服务端 26/15?/26/29/8/29/13
  ⚠️ `test-session.js` 有 1 项跑不了：它要 `spawnSync` 子进程，而本机
  `spawnSync(process.execPath)` 返回 **EBUSY**（node.exe 被锁）。**与本次改动无关**
  （该项测的是"令牌跨进程有效"），换 node 版本后出现，重试无效。
- ⚠️ **Node 路径变了**：`versions/22.22.2-3` → `versions/22.22.2-6`。

### 发布状态（重要）
- 用户选择了「**只发服务端，前端先不动**」，但**服务端自上次发布（16:46）后一行没改**
  （`server/index.js` mtime 16:19 < 16:46）→ **只发服务端等于什么都不发**。
- 修复在 `feishu/js/db-remote.js`（17:30 改），**未构建、未上线** →
  需要跑 `build-feishu.js` 同步到 `server/public` 才能生效，而这一步被 sandbox 拦下并经用户确认暂缓。
- 教训：**"修复在哪个文件"决定发布有没有意义**，被问"要不要发"之前先核对 mtime 与上次发布时间。
