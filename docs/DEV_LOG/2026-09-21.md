## GitHub Pages 上线：从失败到跑通

### 起因
仓库 `henghengzhong7-lab/fever-inventory` 是空的，本地提交没推上去 → Actions 从未触发，Pages 未启用。

### 三个真实故障（按发现顺序）

1. **代理拦截 `github.com`**
   WorkBuddy 沙箱代理（`HTTP_PROXY=127.0.0.1:61506`）间歇性把 `github.com` 拦成
   `CONNECT tunnel failed, response 502`。`api.github.com`、`codeload`、`raw.githubusercontent.com` 不受影响。
   绕开方式：`unset HTTP_PROXY HTTPS_PROXY ...` 走直连（直连同样会间歇性超时）。
   **结论：不能用「代理是否可用」判断网络好坏，要交替重试。**

2. **workflow 缺 `npm ci`**
   测试 `test/test.js` 和 `v1/test/test.js` 都 `require('fake-indexeddb/auto')`，但 workflow 从未安装依赖。
   CI 报 `Cannot find module 'fake-indexeddb/auto'`；本地能过只是因为 `node_modules` 已存在。
   修复：Setup Node.js 之后加 `Install dependencies: npm ci`。

3. **`configure-pages` 的 `enablement: true` 必然失败**
   报 `Create Pages site failed. Error: Resource not accessible by integration`。
   `actions/configure-pages@v6` 的 `action.yml` 原文：
   > This option requires a token other than `GITHUB_TOKEN` to be provided.
   即 `GITHUB_TOKEN` 建不了 Pages 站点，工作流只能部署到**已存在**的站点。
   修复：用有 `repo` 权限的凭据调一次 `POST /repos/{o}/{r}/pages` `{"build_type":"workflow"}`，
   然后从 workflow 里**去掉** `enablement: true`。

### 坑：`github.com` 不通时怎么推代码
用 GitHub Git Data API（`api.github.com` 稳定）：
`POST /git/blobs` → `POST /git/trees`（带 `base_tree`）→ `POST /git/commits` → `PATCH /git/refs/heads/main`。
用普通 push 失败时（每次报错后 `sleep` 重试）才降级走这条路。

### 坑：API 建的提交导致本地/远端 SHA 分叉
远端提交由 API 生成，和本地同名提交 SHA 不同 → 本地 `main` 与 `origin/main` 各一个分支。
`git fetch` 又因网络不通拿不回来。解法：**在本地精确重建那个提交对象**。
关键差异是 **时区偏移**（GitHub 用的是 `+0800`，不是 `+0000`），消息末尾也**不带换行**。
做法：拼出 commit 对象文本 → `git hash-object -w -t commit --stdin` → 校验 SHA 一致 →
`git update-ref`。穷举偏移命中 `+0800`。

注意：本机 `git update-ref refs/remotes/origin/main` 返回 0 但**文件不落盘**
（`refs/remotes/` 目录建了、里面空的）。改用直接写 `.git/refs/remotes/origin/main` 文件解决。

## 线上报「登录状态已失效」→ 定位到网关覆盖 Authorization（16:05 起）

用户验收时报错原文：
> 启动失败：无法打开本机数据库：登录状态已失效，请重新打开应用。
> 请确认是通过「启动」按钮打开的页面，而不是直接双击网页文件。

### 先拆这句话（两段来自不同地方，这个组合就是线索）

- 「无法打开本机数据库：」= `v1/js/app.js:543` 的兜底文案（界面代码，未改）；
- 「登录状态已失效，请重新打开应用」= **`server/index.js` 里 `/api/*` 返回的 401 消息**。

→ 页面**已经是新版**（走的是远程数据层），不是 github.io 旧版；链路前半段是通的，
卡在会话校验。因为 `/api/login` 从不返回 401，所以**登录本身已经成功过**，
是后续请求被拒。

### 真因：网关会给每个请求注入它自己的 Authorization

第一次（错误地）怀疑是会话存在内存里、进程重启导致丢失，于是先加了诊断端点把
服务端**实际收到的请求头**打出来。结果直接推翻了这个假设：

```
我发的是：Authorization: Bearer bogus
服务端收到：Bearer eyJhbGciOiJIUzI1N...   ← 被换成了网关的 JWT
实例一直没变：instance=03a643bc pid=61671（连续三次 + 之后 5 秒都是同一个）
```

请求头里还有 `stgw-request-id`、`eo-connecting-ip`、`cdn-loop`、`x-space-key` 等，
是腾讯 STGW + EdgeOne 网关。**前端发的会话令牌根本到不了服务端**，必然 401。
（纯静态的 GitHub Pages 那条线没有这层网关，所以从来不会遇到。）

### 修复（三层都做，缺一不可）

1. **换传输头**：令牌放 `X-Session-Token`（网关不动自定义头），`Authorization` 同时带一份
   供本地直连用。服务端把两个头都当候选，**逐个校验、谁通过认谁**（`candidateTokens()`）；
   两个都不对才 401 —— 多试一个头不会让伪造令牌混进来。
2. **会话改成自签名无状态令牌**（新增 `server/lib/session.js`）：
   `base64url(载荷) + '.' + base64url(HMAC-SHA256(载荷, 密钥))`，密钥由 `appSecret` 派生。
   原来"发随机串存内存 Map"的写法每次重新部署都会把所有在线队员踢下线
   （**这就是为什么"重新打开又好了、过一阵又坏"**）。改完重启/换实例都不掉线。
3. 前端兜底：`db-remote.js` 收到 401 会调 `FEver.Auth.renew()` **自动重新免登一次再重试**
   （`feishu-auth.js` 新增 `renew()`，用 `renewing` 去重防并发重登）。

- **部署后不要只测 `/api/health`**。它对静态站点够用，对带鉴权的服务会漏掉整条认证链路。
  至少要有一条"用真令牌调受保护接口"的验证。
- **托管平台的网关会改写请求头**。任何自建鉴权都不要只依赖 `Authorization`
  （它是最常被网关/代理接管的头），用自定义头承载，服务端两种都认。
- **排查"认不出身份"这类问题，第一件事是把服务端实际收到的请求头打出来**，
  而不是猜会话/超时/时钟。这次的假设（进程重启）就被实测数据直接推翻了。
- 会话令牌**不要存在进程内存里**，除非能确定单实例且不重启。

## 用户反馈「保存响应很慢」→ 定位到冷启动 + 串行往返（16:43 起）

用户问「后端的计算是在飞书完成，还是在 workbuddy 上完成」。
答：**计算全在本服务（workbuddy 托管）**，飞书只做存储 + 换身份；慢的是往返，不是算。

### 实测把「本地算」和「等飞书」彻底分开

| 环节 | 实测 |
| --- | --- |
| 装载 24 条到内存镜像 + 算全部自增编号 | **0.042 ms** |
| 建主键→record_id 索引 / 解析业务对象 | 0.002 / 0.037 ms |
| 本服务 ↔ 飞书单次往返 | **约 1150 ms**（线上 463 ms） |

→ 本地计算占整条链路 **0.00%**。同一域名下 `tenant_access_token` 只要 280ms、
多维表格接口却要 1100ms，**说明慢在飞书多维表格服务端，不是网络**。

### 真因有两个

1. **6 张表串行拉**：6144ms（原来 `loadAll` 是一张一张 await）。
2. **托管平台会回收闲置容器**：`/api/health` 实测 `uptimeSec=0`、`dataLoaded=false`
   —— 用户隔一段时间再用就是一次冷启动，要等整个加载过程。这才是"保存很慢"的主因。

### 四处优化（都实测验证过）

| # | 做法 | 效果 |
| --- | --- | --- |
| 1 | `loadAll` 6 张表改 `Promise.all` 并行 | 6144ms → **1409ms**（4.4 倍） |
| 2 | `tableIdOf` 合并 `listTables` + 并发锁（`tableIdResolving`） | 省约 0.6s |
| 3 | 写库改**表间并行、表内串行** | 两表 2450ms → **1242ms** |
| 4 | 启动即预热 `loadAll(true)` | 冷启动 6700ms → **1977ms**，且打开页面时已备好 |

**关键实测结论**：原先代码注释写着"多维表格同一个文档下并发读会互相拖慢甚至报错"，
**实测是错的** —— 并行读快 4.4 倍，并行写两张不同的表也不冲突（1242ms）。
写冲突（`1254291`）只针对**同一张表**，所以表内必须串行、表间可以并行。

### 教训

- **怀疑性能问题，先做受控测量把"本地计算"和"外部往返"分开**，不要凭感觉优化。
  这次一测就发现本地占 0.00%，避免了去优化根本不存在的问题。
- **托管平台会回收闲置容器**，诊断线上性能必须看 `uptime`，否则会把"冷启动"
  误判成"接口慢"。
- **不要相信代码注释里的性能假设**（"并发会冲突"），要有实测数据。
- 测真实表之前**先备份 + 事后按 sha256 逐表比对**，这样"无损写测试"才敢做。
