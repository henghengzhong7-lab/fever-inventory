## 第三十轮：修「已经入库的物品不能删除」（连接不上服务器）

### 使用者原话
> 现在已经入库的物品不能删除，显示连接不上服务器，稍后重试。

### 先量，再猜（这一步直接定了性）
| 检查 | 结果 |
| --- | --- |
| 线上服务是否活着 | `/api/health` 正常返回（`instance c13df7f4`，我与调用期间它正好冷启动过一次，之后稳定） |
| 「删除物品」的按钮/拦截逻辑 | 正常：`Rules.blockItemDeletion` 只拦借出/待修，在库物品是可点的 |
| **删除时实际要发出的请求体** | **66,019 字节**（用真令牌只读拉 `/api/data`，照前端两个 op 复刻演算） |
| 浏览器 keepalive 上限 | **65,536 字节**，且多个在飞请求**共享**这 64KB |

→ 不是网络问题，是**请求体越过浏览器上限后被整个拒发**（`TypeError: Failed to fetch`），
`api()` 兜底成「连不上服务器，请检查网络后重试」。

### 两个各自独立的根因（都只在删除这条路上）
1. **`db-remote.js` 的 `flushNow` 给每个写请求都带 `keepalive: true`**。删除的写入带着
   「删除记录」settings 行（每票存一条整条物品快照）—— 全系统唯一持续增长的写入体。
   线上实测 `deleteLog` 122 票、65,384 字节；再删一件就 66KB，越过上限 → **每次删除必失败**，
   失败后 `handleWriteFailure` 重拉数据，物品又回来。其他写入都只有几百字节，所以只有删除中招。
2. **飞书多行文本单元格 ≤10 万字符**（官方文档）。删除记录每票约 500 字符，
   涨到 300 票（`DELETE_LOG_MAX`）会是 14.9 万字符 —— 那一格写不进去，而它和删除在同一个
   写入批次里，日志写失败会把删除一起拖失败。**这一条当时还没爆，是必然会爆的下一颗雷。**

### 改动（两条一起才闭环）
| 文件 | 改动 |
| --- | --- |
| `feishu/js/db-remote.js` | `flushNow` 先量体型再决定要不要 keepalive：`payloadBytes()` 用 `TextEncoder` 数 **UTF-8 字节**（不能用 `String.length`，汉字 length=1、线上=3 字节），`> KEEPALIVE_MAX_BYTES(32KB)` 走普通 fetch。阈值取 32KB 而非 64KB：额度是在飞请求**共享**的，留余量给"一大一小同时在飞" |
| `v1/js/rules.js` | `mergeDeleteLog` 在条数闸（300）之外加**字符闸** `DELETE_LOG_MAX_CHARS=80000`，从最老一票开始丢；**最后一票永远保留**（不能把刚才那次删除记成没留痕） |
| `v1/js/app.js` | 删除记录弹窗的说明文案改实话（可能只留一百多票而不是 300 条） |
| `feishu/test/remote-db.js` | 假后端记录每个写请求的 `{keepalive, bytes}`；新增第 [22] 节 |
| `v1/test/cases/delete.js` | 新增 2 项：体积闸丢最老保最新；单票就超预算时也要留住那一票 |

### 验证
- 新增回归用例**先证明它会红**：把 `useKeepalive` 临时写死成 `true` → `✗ 越过上限的请求没有带 keepalive`；还原后 106/106。
- 飞书数据层 `remote-db.js` **106/106**（原 101），`feishu-auth.js` **36/36**

  `build-pages` + `verify:pages` 18 文件逐字节一致
- 线上体积实测：`deleteLog` 60,699 字符（122 票）→ 在 8 万字符预算内，下一笔删除不会被裁

## 发布这一段：工具说成功，原域名却没动（当天后续）

使用者同意发布后跑了 `workbuddy_sites_deploy`（`server/` 目录）。结果与四步实测：

| 检查 | 原域名 `fever-inventory.app.workbuddy.host` | 发布返回的新链接 |
| --- | --- | --- |
| DNS | 腾讯云 CLB（`clb.bj-tencentclb.cloud`） | 海外 IP（`*.sg2.agentos-app.run`） |
| `Server` 响应头 | `CloudStudio Gateway` | AgentOS |
| 特征串 `KEEPALIVE_MAX_BYTES` | **0（旧代码）** | 3（修复版） |
| 重发一次后 | 仍旧代码 | 新随机域名，**上一个链接立刻 400** |

**定性**：发布工具现在把应用发到 **AgentOS（sg2）**，而线上应用一直在 **CloudStudio**，两套不通；
工具也没找到原应用（`.workbuddy/applications.yaml` 是发布时新建的，只记了今天这个
`wbapp_T3BkBKw7HUjYokVnT2HMZy`），于是新建了一个。`connect_cloud_service` 探过，无可用的临时凭证。

**两条硬事实**（已写进 PROJECT_NOTES「发布平台的分裂」）：
1. 产品**没有"绑定自定义域名"功能**，「设置—数据管理—应用」只能查看/发布/取消发布/删除 ——
   所以"把原域名挪到新应用"这条路在产品层不存在。
2. **AgentOS 的链接每次发布都会变**（同一 appId、同一 sandboxId，随机子域名却换了）——
   "把新域名加进飞书白名单"只能救一次，下次发布又得改。

**给使用者的下一步**（等他定）：① 先在「设置—数据管理—应用」里看有几个 FEver 应用，
有旧的那条就能从那儿重新发布；② 若旧应用不在工具管辖内，只能从 CloudStudio 控制台更新
（先问清当初怎么部署的，可把 `server/` 打包给他）；③ 接受迁域名 + 改飞书白名单（代价见上）。
**在新域名生效前，队员端的删除功能仍然是坏的**，这点已明确告知。

**教训**：发布"成功"≠原域名更新。以后每次发布后必须实测原域名特征串，不能只看工具返回值。
