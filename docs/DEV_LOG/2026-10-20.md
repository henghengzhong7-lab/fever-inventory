## 第三十一轮：把"免费 + 固定域名"的部署通道做出来

背景：10-19 发现发布工具把应用发到了 AgentOS（sg2），与线上的 CloudStudio 不是一套；
且 AgentOS 每次发布换一个随机域名。使用者没有服务器和域名，希望用免费方案。

### 关键判断
**数据在飞书多维表格，后端不存业务数据** → 不需要硬盘、不需要数据库服务器，
只要一个"域名固定、能跑 Node"的免费托管即可。这把可选范围从"必须买服务器"缩到"免费 PaaS"。

启动命令写成 `node server/index.js`。

## 第三十二轮：修「删除显示服务器异常，稍后重试」（线上旧代码的应急修复）

使用者原话："现在我在删除的时候显示服务器异常，稍后重试，你检查一下并解决，解决后需要他能够稳定并长期工作下去。"

### 定性（先量后猜；与第三十轮同一根因，这次拿到了精确数值）
| 检查 | 结果 |
| --- | --- |
| 线上是否活着 | `/api/data` 正常（items 221 / transactions 235） |
| 线上 `deleteLog` | **122 票 / 65,317 字节（63.8 KB）** |
| 删除请求体（复刻前端那两个 op） | **约 65,599 字节** |
| 浏览器 keepalive 上限 | **65,536 字节**（且在飞请求共享） |

**只超 63 字节** → 请求被浏览器整个拒发 → 前端兜底成"服务器异常/连不上，稍后重试" → **每次删除必失败**。
第三十轮的修复代码（体积闸 `KEEPALIVE_MAX_BYTES=32KB` + 字符闸 `DELETE_LOG_MAX_CHARS=80000`）
**已在仓库里写好，但发不到这个地址**（发布工具把应用发到 AgentOS，旧域名在 CloudStudio，两套不通）
→ 所以只能从**数据侧**救。

### 做了三件事
1. **新增 `scripts/trim-delete-log.js`**（运维脚本，可重复执行）：默认 dry-run 预览，`--apply` 才写；
   写前把**完整原值**备份到 `backup/trim-<时间>/deleteLog-before.json`；只动 settings 的 `deleteLog` 一行；
   **最后一票永远保留**；写后回读校验票数。
2. **执行修剪**：122 票 → **30 票**，65,317 → **19,348 字节**；预估删除请求体 65,599 → **19,648 字节**（余量 45,888）；
   备份 `backup/trim-20261020_04150/deleteLog-before.json`。
3. **等价验证写通道**：构造与删除等体量的请求（把 deleteLog 原值幂等写回、**不改数据**）
   → **HTTP 200 / 2669ms**，回读仍是 30 票 / 19,348 字节 ✓ 说明这个体量能通过。

### 长期稳定（使用者明确要求"稳定并长期工作"）
- **已建每周自动任务**：「FEver 物资管理 · 每周修剪删除记录」（每周一 09:00，id `391b1bc7`）。
  先预览；字节数 ≥ 40000 才 `--apply`，< 40000 只记录不动。
- ⚠️ **这只是把问题推后**：deleteLog 会重新增长（历史约 5.5 票/天），30 票涨回 122 票约需 **17 天**；
  每周修剪一次可保证**永远到不了 122 票**。
- **根治要靠部署修复版代码**（体积闸让"超 32KB 的请求不带 keepalive"→ deleteLog 涨到 200 票也能删）。
  通道现状：旧域名发不上去；Render 方案已就绪（第 31 轮 `verify-deploy.js` 实测可行）但需使用者操作。

### 教训
"修好了代码"不等于"问题解决了"——**上线通道不通时，必须找数据侧的临时解法**，
并把"临时解法什么时候失效"算出来（这里约 17 天），交给定期任务兜住。

## 第三十三轮：删除记录上限 300 → 50（使用者提出的方案，已核实并落地到代码）

使用者问："删除记录只需要保留最近的 50 条就可以，如果加上这个条件，是不是就不需要更改任何东西就可以保证应用长期运行下去"

### 先算清楚 50 条够不够（线上真实数据，平均 645 字节/票）
| 保留 | 删除请求体 | 结论 |
| --- | --- | --- |
| 30 | 19.2 KB | ✓ 余量 44.8 KB |
| **50** | **31.8 KB** | **✓ 余量 32.2 KB ← 采用** |
| 80 | 50.7 KB | ✓ 余量 13.3 KB（偏紧） |
| 100 | 63.2 KB | ⚠️ 余量仅 0.8 KB |
| 122 | 77.1 KB | ❌ 超限（本次故障现场） |

**结论：50 条足够安全**；而且它是**硬上限**，意味着体积**永远不会再涨**。

### 但"不需要更改任何东西"不成立 —— 两点必须说清
1. **代码里原本是 300 条**（`DELETE_LOG_MAX = 300`）。要让它自动只留 50，
   **必须改这一行并部署**；而部署通道不通（旧域名在 CloudStudio、工具发到 AgentOS），
   所以线上还得靠**定期修剪**（已建的每周任务）维持。
2. **即使删除永远不出问题，还有一个与它无关的长期瓶颈**：`/api/data` 返回**全量数据**，
   实测 **253 KB**（items 120 / transactions 63 / requests 31 / settings 22 / invoices 12）。
   按流水约 10 条/天，**三年后可能到 4~5 MB**，打开应用明显变慢（手机更明显）；
   飞书单表 2 万行约 5 年才碰到 → **时间点上是"先变慢、后写不进"**，届时需要增量同步/分页。
