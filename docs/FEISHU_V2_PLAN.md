# 飞书共享版改造方案（V2）

> 目标：队员在飞书里打开这个应用，都能登记物资，**所有人看到的是同一份数据**。
> 已确定：数据放**飞书多维表格**，入口限定在**飞书客户端内**。
> 状态：设计待确认，代码未开始（缺飞书应用凭证，无法联调）。

---

## 一、结论先行

接入飞书开放平台解决的是**身份与权限**，它本身**不提供**共享存储。现在的应用是纯静态前端，
数据存在每个人自己浏览器的 IndexedDB 里——这是"每人一份"的根因。

所以这次改造是两件事，缺一不可：

| | 做什么 | 靠什么 |
| --- | --- | --- |
| 身份 | 知道"当前是谁"，并限制只有队员能进 | 飞书自建应用 + 网页应用免登 |
| 共享 | 所有人读写同一份数据 | 飞书多维表格 + 一个薄后端 |

**为什么必须有后端**（三条硬约束，绕不开）：

1. 换 `user_access_token` 需要 `app_secret`，**绝不能进前端代码**（前端代码是公开的）。
2. 读写多维表格必须带 `access_token`，前端拿不到。
3. "谁改的""能不能改"这类校验，只能服务端做。

结论：**保留现有界面，加一个只做三件事的小后端**——换 token、读写 Base、记录操作人。
界面代码（`views*.js`、`rules.js`、`stats.js`、`modules/*.js`、`ui.js`、`qr.js`）**一行都不用改**。

## 二、目标架构

```
飞书工作台
   │ ① 队员点击应用图标
   ▼
飞书客户端（H5 容器）
   │ ② 打开网页应用主页 URL
   ▼
前端：现有 v1 界面 + 飞书登录层 + 远端数据层
   │ ③ tt.requestAccess() 拿 code（5 分钟有效）
   │ ④ 带 code 请求后端
   ▼
后端：云函数（持 app_secret）
   │ ⑤ code → user_access_token → 用户信息（open_id / 姓名）
   │ ⑥ 校验是否队员 → 签发本系统 session
   │ ⑦ 把前端的增删改查翻译成多维表格 API
   ▼
飞书开放平台 OpenAPI
   ▼
飞书多维表格（全队共用一份数据）
```

### 组件与改动量

| 组件 | 来源 | 改动 |
| --- | --- | --- |

关键设计：**数据层接口保持不变**。现有代码到处在调 `DB.getAll('items')`、`DB.add('transactions', ...)`，
只要 `db-remote.js` 提供同样的函数签名，上层完全无感。


## 三、数据模型 → 多维表格

一个多维表格（Base）里建 7 张表，一张对应一个 store：

| 表名 | 主键 | 说明 |
| --- | --- | --- |
| `categories` | `id` | 机械 / 电控 / 视觉 / 硬件四大类 + 专属字段定义 |
| `lots` | `id` | 同款共用身份的库存账（按"款"聚合） |
| `items` | `code` | 物品身份，一物一码 |
| `purchaseRequests` | `id`（自增） | 采购申请，含状态流转 |
| `invoices` | `id`（自增） | 发票台账 |
| `transactions` | `id`（自增） | 出入库流水，**这是并发最集中的表** |
| `settings` | `key` | 键值配置 |

需要注意的迁移点：

- **自增 ID 在 Base 里没有**。Base 的 record_id 不可自定义，所以 `purchaseRequests / invoices / transactions`
  的 `id` 要在后端生成：维护一张 `counters` 表，或用"读取当前最大号 + 1"，并在后端串行化（见第六节风险 1）。
- **字段类型要映射**：Base 的数字/日期/单选/人员字段有独立类型，不能都塞多行文本。日期存时间戳（毫秒），
  人员字段存 open_id（这样"谁借出的"在飞书里能看到头像和姓名，是接飞书最大的红利）。
- **`settings` 表**用来放 `lastBackupAt` 这类键值，保持一个小表即可。

### 顺带得到的能力

数据进了多维表格，飞书里可以直接用**视图、筛选、仪表盘**做统计，不用再写代码；
队员在飞书里也能直接打开表格查，不必进网页应用。

## 四、后端接口契约

只需要 5 个端点，全部要求带 `Authorization: Bearer <session>`（除 `/login`）：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| POST | `/login` | 入参 `{code}`，出参 `{token, user:{openId,name,avatar}}` |
| GET | `/data` | 一次拉全部表（物品/流水/申请/发票/大类/设置），用于前端启动时建内存镜像 |
| POST | `/write` | 入参 `{ops:[{type:'add'\|'put'\|'delete', store, data\|key}]}`，一个请求内顺序执行 |
| GET | `/me` | 校验 session 是否还活着 |
| POST | `/backup` | 可选：服务端直接产出整包 JSON（比前端导出更可靠） |

设计取舍：

- **一次性拉全表 + 前端内存镜像**，而不是每次查询都打后端。战队规模（千级记录）一次几百 KB，
  比"每个页面切换都发请求"快得多，也最贴近现有代码的写法（现有代码就是 `getAll` 然后前端过滤）。
- 写操作走 `/write`，支持一次提交多表（对应现有代码的 `runTx` 多表原子写）。

## 五、飞书后台要配置什么

这部分只能你和飞书管理员做，我做完代码后需要这些值才能联调：

1. **创建自建应用** → 拿到 `App ID` / `App Secret`。
2. **添加能力**：网页应用（H5）。填入应用主页 URL。
3. **安全设置 → 重定向 URL**：必须填**完整路径**（不含 `?` 和 `#`）。
   这是最容易踩的坑——填错会直接报 `10236`，前端免登失败。
4. **权限管理**：至少要有
   - `authen:user.id`（获取用户身份）
   - `bitable:app`（读写多维表格）
   - 读通讯录（可选，用于校验"是不是队员"）
5. **可用范围**：设为战队成员或某个部门/群，这样非队员根本看不到这个应用。
6. **发布版本**，并等管理员审批通过（企业内应用通常一次即可）。

## 六、必须提前知道的四个风险

### 1. 并发写（最需要认真对待）

多维表格**没有事务**，也没有自增锁。两个队员同时借出同一件物品，可能出现数量算错。
现有代码的 `runTx` 在 IndexedDB 里是原子的，搬到远端后这个保证会消失。

处理办法（后端实现，按优先级）：

- 所有写请求在**同一个实例内串行**（云函数单实例队列 + 写队列），这是最低成本的方案；
- 关键表（`items`、`lots`）加 `version` 字段做乐观锁，冲突时返回明确提示让用户重试；
- 数量增减改成"读-改-写"全在后端一次完成，前端只提交意图（"借出 1 件"），不提交结果数量。

### 2. 频率限制

多维表格接口有频率限制（写入约 50 次/秒、批量查询约 20 次/秒，批量查询单请求约 50 条）。
战队规模完全够用，但**不能**在前端循环逐条写，必须批量提交。

### 3. 免登只在飞书客户端内可用

`window.tt` 只在飞书 H5 容器里存在。队员如果拿普通浏览器打开这个网址，会没有免登能力。
需要在前端做环境检测：不在飞书里就显示一段明确提示（"请在飞书工作台打开"），
而不是白屏或报错。

### 4. 数据在飞书里，权限粒度受版本限制

- 多维表格的**高级权限（行级/字段级）需要商业版及以上**。免费版只有文件级权限
  （可管理 / 可编辑 / 可阅读）。
- 所以"能不能进系统"用飞书应用可用范围控制；
  "谁改了什么"靠后端在每条记录上写 `updatedBy`（open_id）来满足审计。
- 如果以后需要"队员只能改自己登记的东西"，那要么升版本，要么在后端拦。

## 七、与现有版本的关系

| | 本地离线版（现状 v1） | 飞书共享版（本次） |
| --- | --- | --- |
| 数据位置 | 浏览器 IndexedDB | 飞书多维表格 |
| 是否共享 | 每人一份 | 全队一份 |
| 是否需要网络 | 不需要 | 需要 |
| 谁用 | 单人离线登记、现场无网时 | 日常协作、多人同时登记 |
| 保留 | **保留**，界面同一套 | 新增构建产物 |

两版共用同一套界面代码，靠构建脚本区分，避免"改一个功能要改两遍"。

## 八、待你确认的两点

1. **后端托管在哪**
   推荐**腾讯云 CloudBase**（云函数 + 静态托管）：国内访问快、有免费额度、能一站式部署。
   备选：任意一台能跑 Node 的服务器（若有现成的）。需要你用腾讯云账号开通并授权。
   ⚠️ 不建议用 GitHub Pages 之外没验证过的海外 Serverless，国内访问和飞书客户端回调都可能不稳。

2. **前端是否也一起迁到国内托管**
   现在前端在 `github.io`。国内网络访问 `github.io` 经常不稳定，飞书客户端里加载慢或打不开的风险真实存在。
   建议前端一起迁到 CloudBase 静态托管（改动很小，构建产物原样上传），
   GitHub Pages 保留为备用地址。
