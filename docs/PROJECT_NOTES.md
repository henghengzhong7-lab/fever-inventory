## 项目定位
FEver 战队（机器人战队）的物资管理系统，**两套并行**：
- **本地离线版**（`v1/`）：纯静态前端 + 浏览器 IndexedDB，无后端无登录，不共享数据。
  入口 `启动物资管理.bat`，端口 **8321**。**现场没网时仍可用，不要动它。**
- **飞书共享版**（`feishu/` + `server/`）：全队共用一份数据。界面代码与离线版**完全同一份**
  （`v1/` 的运行时文件一行未改），只换数据层。

## 飞书共享版（架构与硬限制）
- **免费版多维表格没有行级/字段级高级权限**（需商业版）："谁能进"靠应用可用范围，"谁改过"靠记录上的操作人字段。
- 单表最多 **20,000 条**（流水增长最快）；写 50 次/秒；**同一张表并发读写会 `1254291 Write conflict`**。
  ⚠️ **不同表之间并行是安全的**（读并行快 4.4 倍、写并行不冲突），冲突只在同一张表上。
- 字段名必须完全匹配，否则 `1254045`；多行文本读出是 `[{text,type}]`，写入可直接给字符串。
- 存储设计（`server/lib/store.js`）：每张表只有 5 列（主键/摘要/数据(整条 JSON)/更新时间/操作人）。
  业务字段不逐列展开 —— 加功能不加列。
- **并发方案**：所有写请求走一条串行队列；**编码由服务端发号**（见「发号机制」一节）。
- **上线流程**（已跑通）：`npm run init:base` → `build:feishu` → 发布 `server/` → 用户把主页地址与
  重定向 URL 填成线上地址并发布。

### 飞书接口踩坑（都实测过）
- 新建多维表格自带一张「数据表」，里面有 **10 条全空记录**（`fields = {}`）→ 判断"空表"要数**非空记录**。
- 改名/删除多维表格**不在 bitable API 里**（`PATCH|DELETE /open-apis/bitable/v1/apps/:token` → 404）；
  但 `GET /open-apis/drive/v1/permissions/{token}/members?type=bitable` **不需额外权限**就能读。
- `tt.requestAccess` **不需要网页应用鉴权**（免签、免配 H5 可信域名）；但 `tt.scanCode` **必须鉴权**。
- 免登页面地址必须加进「安全设置 → 重定向 URL」，否则授权被拒。
- 权限没开时返回 `99991672`，报文里自带开通链接。
- `im:message` 只是权限、不够：还要「应用功能→机器人」启用 + **权限变更后创建版本并发布**，否则私聊收不到。
- **登录名单必须存多维表格设置表**（key=`knownUsers`）：本地 `known-users.json` 在发布目录里，
  重新发布会把它清掉，靠姓名写的 `admins` 就反查不到 openId 了。loadAll 时合并、rememberUser 时写回。

### 排错顺序（飞书侧）
`cd server && npm run check`（只读，打印**原始返回**含 `permission_violations`）。

### 托管平台网关的坑（影响所有自建鉴权的服务）
平台网关会给每个请求注入它自己的 `Authorization`，把前端的 `Bearer <我们的令牌>` **整个覆盖掉**。
→ **自建鉴权的令牌不能只放 `Authorization`**，要用自定义头（这里是 `X-Session-Token`）；
服务端两个头都当候选、逐个校验、谁通过认谁。**这个问题只在托管服务上出现**，静态线（Pages）没有网关。
（相关：`server/lib/session.js` 是**自签名无状态令牌**，密钥由 `appSecret` 派生 ——
不要改回"发随机串存内存 Map"，那样每次重新部署都会把所有在线队员踢下线。）

### 排错顺序（认证类）
1. **先把服务端实际收到的请求头打出来**（不要先猜会话/超时/时钟）。
2. 看服务端返回的确切文案出自哪个文件（界面兜底文案与服务端消息拼在一起时，分段能判断链路走到哪）。
3. 部署后**不要只测 `/api/health`**，至少要有一条"用真令牌调受保护接口"的验证。

## 性能（已实测：时间全花在飞书往返，不在计算）
计算全在本服务，飞书只做存储。装载全部数据到内存镜像 + 算自增编号 + 建索引 + 字段转换 ≈ **0.08ms**；
本服务 ↔ 飞书单次往返：本地约 1150ms、**线上 463ms**（同域下 token 只要 280ms → 慢在飞书的表服务）。

### 四处优化（都在代码里，别再退回去）
1. `loadAll` 6 张表 `Promise.all` 并行 → 6144ms → **1409ms**
2. `tableIdOf` 合并 `listTables` + 并发锁（否则并发时打出 6 个请求）
3. **写库表间并行、表内串行** → 两表 2450ms → **1242ms**
4. **启动即预热** `loadAll(true)`（`server.listen` 回调里）→ 冷启动 6700ms → **约 2s**
⚠️ 原 `loadAll` 注释写"同文档下并发读会互相拖慢甚至报错"——**实测是错的**，别看注释改回去。
⚠️ 托管平台会**回收闲置容器**（`uptimeSec=0`、`dataLoaded=false`），隔一段时间再用就是一次冷启动 ——
这是使用者感受到"慢"的主因。

## 发号机制（第二十六 + 二十八轮，解决"编号被占用/添加卡顿"）
**根因（两半，第一半修完才发现第二半）**：所有"唯一标识"原来都是**前端在本机算的** ——
① 物品编码（`Rules.nextCodes` 读本地 settings 计数器）；② 申请号/发票号/流水号
（`db-remote.js` 的 `allocateKey` 读本机 `counters`）。
两人同时操作就分到同一个号 → 服务端 `requireNewKey` → 409 → 前端提示"请重新操作一次"并重拉全量（1.4s）。
⚠️ **每次添加物品都会写一条入库流水** → 流水 id **几乎必然**撞（编码要"同前缀同号"，概率小得多的）。
所以只修编码那一半，使用者根本感觉不到变化。

**现在两者都由服务端发号 + 前端领一段**：
- `server/index.js`：公共内核 `allocateSpan(counterKey, count, computeBase, actor)`（算号 + 水位落库）；
  `allocateCodes`（水位 `codeCounter:<前缀>`）与 `allocateIds`（水位 `idCounter:<表名>`）都用它。
  接口 `POST /api/reserve-codes` / `POST /api/reserve-ids`，都包在 `enqueue` 里。
  ⚠️ 内核函数**不进队列**（`enqueue` 内再 `enqueue` 会死锁）。
  ⚠️ 算水位取 **`max(水位, 数据里实际最大值)`** —— 只看水位，手工导入过大号记录后会发出已占用的号。
- `db-remote.js`：两个内存号池（编码 `RESERVE_CHUNK=20`、id `ID_RESERVE_CHUNK=5`）。
  段大小不同的理由：**记录号是显示给使用者看的**（申请 #12），一次领 20 会跳过一大段看着怪。
  `loadAll` 成功后 `prewarmIds()` 预热（池里有货时不发请求，所以反复 reload 不浪费号）。
  ⚠️ 取号时要**跳过本地镜像里已存在的号**（预留号可能被导入备份/别的设备顶掉）→ 宁可跳号不撞主键。
- 离线版：`DB.nextCodes` 用原本地事务逻辑（单机无并发）；`Rules.nextCodes` 委托给它。
- ⚠️ **代价：号会跳号**（编码与记录号都会）。只是标识，不影响扫码/统计/标签。
- ⚠️ **两份假后端都要加新接口**：`feishu/test/fake-backend.js`（端到端页共用）
  与 `feishu/test/remote-db.js`（数据层自带）。⚠️ 两者风格不同：前者数据在 `backend.data`、
  用 `resolve(response(...))`；后者数据在 `data`、直接 `return response(...)`，且入参变量叫 `init` 不叫 `options`。
- ⚠️⚠️ **预热/填充只能用"检查+补"，绝不能拿消费型接口去填**：我一度把  写成

## 发布平台的分裂（2026-10-19 实测，动手发布前必读）

**现象**：第三十轮修复发布"成功"（工具返回 `verified:true` + 新链接），但
`fever-inventory.app.workbuddy.host` 拿到的**仍是旧代码**，删除功能在队员端照旧坏着。

**实测证据（三条一起才定性）**：

| 检查 | 原域名 | 发布返回的新链接 |
| --- | --- | --- |
| DNS | 腾讯云 CLB（`clb.bj-tencentclb.cloud`） | 海外 IP（`*.sg2.agentos-app.run`） |
| 响应头 Server | `CloudStudio Gateway` | AgentOS |
| 本轮特征串 `KEEPALIVE_MAX_BYTES` | **0 处（旧代码）** | 3 处（修复版） |

**根因**：`workbuddy_sites_deploy` 现在把 `server/` 发到 **AgentOS（sg2）**，而线上应用在
**CloudStudio**。两套平台不通，工具也**没有找到原应用**（`.workbuddy/applications.yaml` 是发布时
新建的，只记了今天这个 `wbapp_T3BkBKw7HUjYokVnT2HMZy`；原应用记录不在本工作区），于是**新建了应用**。
`connect_cloud_service` 探过：无可用的临时凭证，云服务通道也走不通。

**两个必须记住的事实**：
1. **产品没有"绑定自定义域名"这个功能** —— 「设置—数据管理—应用」只能查看/发布/取消发布/删除。
   所以"把原域名挪到新应用"这条路**在产品层不存在**。
2. **AgentOS 的应用链接每次发布都会变**：两次发布同一个应用（appId 不变、sandboxId 也不变），
   但随机子域名从 `91908b…` 变成 `c6abc2…`，**上一个链接立刻失效（HTTP 400）**。
   → 意味着"把新域名加进飞书白名单"这招只能救一次，下次发布又得改一遍。

**教训**：发布后**只看工具返回成功不算数**，必须实测原域名的特征串（老规矩四步照跑）。
这次就是"工具说成功、原域名纹丝不动"。

**下次怎么办**（按优先级）：
1. 让使用者在「设置—数据管理—应用」里确认有**几个** FEver 应用 —— 有旧的那条就能从那里重新发布；
2. 若旧应用记录确实不在工具管辖内，只能从 **CloudStudio 控制台**侧更新（先问清当初怎么部署的）；
3. 若最终接受迁域名：把当次发布的新域名加进飞书「重定向 URL + H5 可信域名」并发布应用版本 ——
   但要接受"每次发布域名都会变"这个代价，发布要低频。



**现象（使用者 2026-10-19 原话）**：「现在已经入库的物品不能删除，显示连接不上服务器，稍后重试」。

**根因不是网络，是两处体型限制，而且都只在删除这一条路上出现**：

1. **浏览器 keepalive 的 64KB 正文上限**。`db-remote.js` 的 `flushNow` 给每个写请求都带
   `keepalive: true`，而浏览器规定 keepalive 请求正文 **≤64KB**（同一时刻在飞的多个 keepalive
   请求**共享**这 64KB），**超限不降级 —— 整个请求被拒**（`TypeError: Failed to fetch`），
   于是 `api()` 的兜底文案「连不上服务器，请检查网络后重试」就出现了。
   线上实测（真令牌读 `/api/data`）：删一件物品的写请求体 **66,019 字节 > 65,536**，
   所以**每一次删除都必失败**，重拉数据后物品又回来。中招的只有删除，是因为删除的写入
   带着「删除记录」settings 行（每票一条整条物品快照）—— 这是全系统**唯一持续增长的写入体**，
   别的写入（预算、草稿）都只有几百字节。
2. **飞书多行文本单元格 ≤10 万字符**（官方文档）。删除记录每票约 500 字符，122 票已 60,699
   字符，涨到 300 票会是 14.9 万字符 —— 那一格写不进去，而它和删除在同一个写入批次里，
   日志写失败会把删除一起拖失败。

**修法（两条一起才闭环）**：
- `feishu/js/db-remote.js`：`flushNow` 先量体型再决定要不要 keepalive。数的是 **UTF-8 字节**
  （`TextEncoder`，不能用 `String.length` —— 一个汉字 `length` 是 1、线上是 3 字节，
  拿 length 比会把明显超限的请求误判成"还能用"）。阈值 `KEEPALIVE_MAX_BYTES = 32KB`
  而不是 64KB：额度是在飞请求**共享**的，得给"一大一小同时在飞"留余量。大的走普通 fetch，
  照样发得出去，代价只是"点完确认瞬间关页面"那一下可能被打断。
- `v1/js/rules.js`：`mergeDeleteLog` 在条数闸（300）之外加**字符闸**
  （`DELETE_LOG_MAX_CHARS = 80000`），从最老一票开始丢；**最后一票永远保留**
  （不能为了省体积把刚才那次删除记成没留痕）。

**教训**：
- 「连不上服务器」只说明 **fetch 被拒**，不代表服务器坏了（当时 `/api/health` 好得很）。
  这类网络层文案出现时，先量服务端和请求体，别先怀疑网络。
- 任何带 `keepalive` 的请求都要问一句：**这个请求体有没有可能长大**。会大的只有
  "读—改—写"累加的 settings 键（这个系统里就是 `deleteLog`）。
- **审计日志和主操作放进同一个写入批次，日志的失败会拖死主操作**：`setSettingSafe` 本来
  设计成"日志失败不影响主操作"，但批次合并让这个设计失效了。这是**仍待收敛的设计债**
  （_options：删除等服务器确认后再单独记日志_），记在 DEV_LOG 待办里。

## 删除链路的体积闸（第三十 / 三十二轮，最容易复发的故障）

**现象**：删除物品时页面报「服务器异常」或「连不上服务器，稍后重试」，**每次删除必失败**，物品又回来。

**根因**：删除的写请求是「删物品 + 写 deleteLog」**同一个批次**发出的，前端写请求带 `keepalive`，
而浏览器对 keepalive 的上限是 **65,536 字节**（且在飞请求**共享**这一份额度）。
`deleteLog` 每票存**整条物品快照**，是全系统唯一持续长大的写入体。
2026-10-20 实测：122 票 / **65,317 字节** → 删除请求体 **65,599 字节** → 只超 63 字节 → 请求被整个拒发。

**两道闸（都在仓库里，但线上旧版没有）**：
- `feishu/js/db-remote.js`：`flushNow` 先量体型（`TextEncoder` 数 **UTF-8 字节**，不能用 `String.length`），
  超过 `KEEPALIVE_MAX_BYTES = 32KB` 就不带 keepalive。阈值取 32KB 而非 64KB —— 额度是共享的，要留余量。
- `v1/js/rules.js`：`mergeDeleteLog` 除了**条数闸（`DELETE_LOG_MAX = 50`）**，还有**字符闸** `DELETE_LOG_MAX_CHARS = 80000`
  （飞书多行文本单元格上限 10 万字符），从最老一票开始丢，**最后一票永远保留**。

**线上旧版的应急手段：`node scripts/trim-delete-log.js`**
- 默认 dry-run 预览；`--apply` 才写；写前把完整原值备份到 `backup/trim-<时间>/deleteLog-before.json`；
  只动 settings 的 `deleteLog` 一行；最后一票永远保留；写后回读校验。
- 保留 30 票时约 19KB，删除请求体约 19.6KB（余量约 45KB）。
- ⚠️ **这是把问题推后**：deleteLog 会重新增长（历史约 5.5 票/天），30 票涨回 122 票约需 **17 天**。
  已有每周自动任务「每周修剪删除记录」（周一 09:00，字节数 ≥ 40000 才修剪）兜住。
- **根治**：部署带体积闸的修复版代码。

**教训**：`keepalive` 的 64KB 是**浏览器硬限制**，不是服务端能放宽的。
凡是"请求体可能持续变大"的写入，都要先量体型再决定要不要 keepalive。

### 为什么上限是 50 条（2026-10-20 实测依据）
每票带整条物品快照，线上实测平均 **645 字节/票**。删除请求体上限 65536 字节：

| 保留票数 | 删除请求体 | 结论 |
|---|---|---|
| 30 票 | 约 19.2 KB | ✓ 余量 44.8 KB |
| **50 票** | **约 31.8 KB** | **✓ 余量 32.2 KB（选定值）** |
| 80 票 | 约 50.7 KB | ✓ 余量 13.3 KB（偏紧） |
| 100 票 | 约 63.2 KB | ⚠️ 余量仅 0.8 KB |
| 122 票 | 约 77.1 KB | ❌ 超限，每次删除必失败 |

取 50 而不是贴近上限：keepalive 额度是**在飞请求共享**的，要留一半给"一大一小同时在飞"。
50 票已足够追溯最近几十次删除（原先按 300 留，实际用不到）。

### 全量同步的长期瓶颈（与删除无关，但影响"长期运行"）
`/api/data` 会返回**全量数据**，2026-10-20 实测 **253 KB**（items 120 / transactions 63 /
requests 31 / settings 22 / invoices 12 / categories 5）。按流水约 10 条/天增长，
**三年后这个响应可能到 4~5 MB**，打开应用会明显变慢（尤其手机网络）。
飞书单表 2 万行的硬限制大约 5 年才会碰到，**所以时间点上是"先变慢、后写不进"**。
到时需要做增量同步或分页 —— 属于架构改动，不是现在的问题。

## 端到端测试的纪律（本项目踩坑最多的地方）
- **等待条件必须锚"页面标识"**（`#view-root` 的 `data-page`）或唯一元素，**不要锚文字**：
  等待条件在**旧页面**上就为真 → 点击落在旧闭包上（拿的是旧数据）。
- **同路由 `App.goto` 是原地重渲染**：要重进同一个页面，先 `goto` 别的页、确认 `data-page` 变了再进。
- **别让新用例改动后面用例依赖的数字**（只验证"能发起操作"时，打开弹窗看一眼就取消）。
- **用例要放在它依赖的数据产生之后**（首页跑在采购之前，那时还没有发票附件）。
- **断言用相对值**（比之前多了几次），别写死"等于 N 次"；同名事物的绝对数字会被前一条用例影响。
- `#toast-root` 会残留前面用例的提示 → 断言"没有提示"前先 `innerHTML = ''`。
- **改名的物品/字段别和断言文字撞**：我曾把测试件命名为"添加人测试件"，导致"等出现添加人"当场为真。
- **不要靠给 `window.print` 打桩数调用次数**判断打印是否发生（无头浏览器里它是空操作，桩拦不到）。
- **往测试文件插代码**：锚定**一句唯一的完整语句**（如某条 `E2E.ok(...)` 整行），
  **不要用 `indexOf('    });')` 之类结构特征定位**（会切到用例内部，插完多出孤立括号、语法错 —— **栽过两次**）；
  `E2E.finish()` 在文件里**出现两次**（主流程 + catch 块），别用 `lastIndexOf` 找插入点。
  **改完必须** `node --check` + `grep -c "await E2E.record"` 核对用例数没变。
- 测试文件是"已修改未提交"状态时**不能用 `git checkout` 兜底**（会丢掉当天全部测试改动）。

## 代码层的通用规矩
- ⚠️ **`guard()` 只透传第一个参数**：对外的 `Ops` 方法要多参数时必须**收一个对象**
  （`(codes, options)` 会让第二个参数永远是 `undefined` —— 栽过两次，连"从没被用过"的
  `approveRequests(ids, input)` 都因此清掉了）。
- ⚠️ **别把字段校验写进 `runTx` 回调**：同步抛错会走 `db.js` runTx 的"同步异常"分支，
  它没接住自己 abort 出来的"事务被中断" → 未处理拒绝 → **进程直接崩**。校验一律放函数开头。
- ⚠️ **`deleteLog`（删除记录）是"读当前→合并→写回"**：必须放在**同一个事务**里，
  或放在事务**之后**（塞进同一事务里会再开事务，IndexedDB 直接挂）。
- ⚠️ **路由参数会丢**（`Views.xxx(params)` 要过 `goto → routeToHash → hash → hashToRoute`）：
  ① `ROUTES` 表要透传 `p`；② 要进地址栏就在 `routeToHash`/`hashToRoute` 各加一条。
  漏了**不报错**，只是"预置条件没生效"。
- ⚠️ **弹框里的跳转要自己关弹框**（全局分发只 `goto`、不关弹框 → 弹框盖在新页面上像"点了没反应"）。
  做法：`openModal` 的 `onMount` 里局部监听 `[data-goto-item]` 并 `close()`（局部先于 document 执行）。
  另外 `[data-cancel]` **不会自动绑定**，要手动绑。
- ⚠️ **"保住已填内容"式回填，必须排除掉你正要改的那个字段**（切大类时把旧 `categoryId` 写回去 →
  表现是"点了没反应"）。
- ⚠️ **改了默认配置的字段，先想"老库里的那一行怎么办"**：`initCategories` **只补缺的大类、不覆盖已有的**，
  所以改默认值只对新库生效（老库要靠定向幂等的迁移函数，如 `fixVisionCalibration`）。
- **枚举型字段的筛选选项要列全量**（只有"从数据里来"的字段如申请人，才用 `distinctOf` 从数据收集）。
- **加了新前端文件**要接四处：`v1/index.html`、`scripts/pages-files.js`、`scripts/feishu-files.js`、
  **`v1/test/e2e/*.html`（9 个页面各自列 script）**。
- **加了新服务端接口**：`feishu/test/fake-backend.js`（端到端页共用）与 `feishu/test/remote-db.js`
  （数据层自带）**两份假后端都要加**。
- **给表格加列前**，先搜一遍测试里有没有按**列号**取值的断言（`children[1]` 这种会全错位）。
- **导出/打印/单据的口径函数只写一份**（如 `Rules.txnLabel`、`Stats.rangeStart`），
  多处共用，别各写一套（否则明细加起来的数跟表格对不上）。
