## 2. 已上线的内容（按轮次）

### 第二十四轮 —— 同名归同一大类 + 视觉类不做标定
| 需求 | 实现 |
|---|---|
| 相同名称的东西要所属一类 | 新增物品时若已有同名物品，**所属大类自动带成它所在的那个**并提示；同名散在多个大类时如实列出件数。使用者手动改过大类后不再自动切。编辑物品改名撞名只提示（大类本就不可改）。 |
| 视觉的物品不需要标定，直接删除 | 视觉类页的**标定看板整块删除**、列表标定列、标定状态筛选、首页「待标定/需重标」指标、首页「尚未标定」提醒、物品详情标定信息，全部移除。物品上已存的 `calibrationStatus` / `lastCalibrationDate` **保留在数据里**，只是不显示不提醒。 |

关键点：标定的开关在**大类定义**里，只改默认值无效（`initCategories` 只补缺的大类、不覆盖已有的），因此额外做了**定向幂等迁移** `fixVisionCalibration()`。

### 第二十五轮 —— 兵种表扩充 + 预算口径修正
| 需求 | 实现 |
|---|---|
| 兵种里再加「英雄」「小轮腿」 | 纯新增、旧的全部保留，历史数据归属分文不动。 |
| 兵种预算里加上其他已经花了的 | 「已用」= **已同意的申请金额 + 直接入库的物品总价**。直接入库的东西（新增物品时填的「总价」）也是真花的钱，以前完全没进预算。页面摊开构成，CSV 拆成两列。 |

⚠️ 代价：申请号/发票号/流水号与物品编码**都会跳号**。

### 第二十六轮 —— 物品编码改由服务端发号（第一半）
前端各自在本机算编码 → 两人同时添加会撞号 → 服务端 409 → 前端提示"请重新操作一次"并重拉全量（1.4 秒）。改为**服务端发号 + 前端领一段存着用**（默认 20 个）。

### 第二十七轮 —— 预算里能看"直接入库"的明细
「已用」格子里原本只有金额、点不开。现在「入库 ¥X 明细」是按钮，弹出该兵种填了总价的物品清单（编码/名称/总价/入库时间/添加人 + 件数合计），每条编码可点进物品详情。时间范围与预算页同口径。

### 第二十八轮 —— 记录 id 也改由服务端发号（第二半）
**上一轮只修了一半**：申请号/发票号/流水号仍是前端本机计数器分配的，而**每次添加物品都会写一条入库流水** → 两人同时添加几乎必然分到同一个流水 id。改为同样由服务端发号（`POST /api/reserve-ids`，段大小 5）。

## 3. ⚠️ 未上线：已修好的"卡顿"修复

### 现象
使用者反馈：**"我一个人用都特别卡"**、**"点开物品详情也很慢，连着点也每次都慢"**。

### 排查结论（这部分请重点看）
先量后猜，逐条排除：

| 检查项 | 结果 |
|---|---|
| 线上 `/api/data`（带真令牌实测） | **62 ms** |
| 数据量 | items 125、transactions 134、purchaseRequests 27 —— 极小 |
| 本服务 ↔ 飞书一次往返 | 208 ms |
| 物品详情页是否发网络请求 | **不发**（只有 `Stats.itemContext` 读内存镜像） |
| 只读事务开销 | `runTx` 只读直接返回，不克隆整表 |
| 常驻轮询 | 无（`setInterval` 只在登录时等飞书 JSSDK，最多 3 秒） |
| 写入后是否重拉全量 | 不重拉（`refresh()` 只 `render` + 刷新角标） |

静态与量测都指向"不该这么慢" → 回头复查自己写的代码，找到死循环。

### 根因：号池"越补越领"的三个缺陷叠加
```js
var pool = 池子.filter(id => !idTaken(store, id));            // ① 过滤本地已占用的号
if (pool.length >= count) { ...; if (池低) 补池; }            // ② 池低就补
return api('/api/reserve-ids').then(() => takeIds(store, count));  // ③ 递归
```
只要"池里领来的号与本地镜像里的号重叠"——**改系统之前是本机计数器造号，与服务端水位本就不一致，这类老数据线上真实存在**——就会进入：
`取号 → 不够 → 领 → 号又被占用 → 再领 → …`
**每一步都是一次 HTTP 请求，且无上限。** 这与"连着点也每次都慢"完全对应；改之前用本机计数器**一次网络都不发**，所以体感反而更快。

### 修法（三条同时成立才算修好）
1. **不递归**——池空时最多领一次；领来的号若已被占用就丢弃，不再重试
2. **过滤只在领号时做一次**——不是每次取号都扫全表
3. **补池节流 30 秒**（`ID_FILL_COOLDOWN`）——死循环的最后一道闸；发领号请求收敛到唯一一处 `fetchIds()`

## 9. 三条教训（写给接手的人）

1. **"把 XX 改成服务端发号"这类改动，先列全"所有唯一标识的来源"再动手。** 我第一次只改了 `nextCodes`（编码），漏了 `allocateKey`（申请/发票/流水号）——两个函数在不同文件、名字也不像，只看一处就会以为改完了。

2. **"预热/缓存填充"只能用"检查 + 补"，绝不能用消费型接口去填。** 我曾把 `prewarmIds` 写成 `takeIds(name, 1)`（那是"取走一个号"、返回值还丢掉），于是每次数据加载都白扔 3 个号，池子两下见底，之后每次写记录都要真去领号 → 单人操作也卡。

3. **改动涉及用户感知的性能路径时，先量各段耗时再改。** 今天连续三次返工，根因都是"只跑测试不量实际耗时"——测试能证明"功能对"，证明不了"快"。
