# FEver 战队物资管理 · 飞书共享版后端

一个无状态的小服务：**换飞书身份、读写多维表格、记下是谁改的**。

它不渲染界面、也不存数据。界面由前端（`server/public/`）提供，数据在你们自己的飞书多维表格里。
所以这个服务可以随时重启、重新部署，数据都不会丢。

---

## 为什么必须有它

接飞书开放平台只解决"身份"，不解决"共享存储"。三条硬约束绕不开：

1. 免登授权码换 `user_access_token` 需要 `app_secret`，而前端代码是公开的，放不了；
2. 读写多维表格必须带 `access_token`，前端同样拿不到；
3. "谁改的"这类审计信息只能服务端写。

## 本地跑起来

```bash
cd server
cp config.example.json config.json     # 然后填 appId / appSecret
npm run init:base                      # 建多维表格和 6 张数据表，并把 app_token 写回 config.json
npm start                              # 默认 http://127.0.0.1:8787
```

`init:base` 重复运行是安全的：已存在的表不会被重建，也不会动里面的数据。

**想让多维表格出现在你自己的飞书空间里**（而不是归应用所有、你在飞书里看不到），
先自己在飞书里新建一个多维表格，把它「添加文档应用」授权给这个自建应用（权限选可编辑），
然后把链接交给脚本认领：

```bash
node init-base.js "https://xxx.feishu.cn/base/AbCdEf123456?table=tblXXX"
```

## 性能：时间花在哪，以及怎么优化的

### 先看结论：一个请求的两端都有硬成本

一次保存要过两道关，**两道都不是本服务能算快的**：

| 环节 | 实测耗时 | 说明 |
| --- | --- | --- |
| 本服务自身计算（装载 24 条到镜像 + 算全部自增编号 + 建索引） | **约 0.08 ms** | 可以忽略 |
| 托管平台网关：浏览器 → 本服务，**每个请求固定** | **约 550 ms** | 下一个 1.4KB 的静态网页也是这个数；TCP 连接复用了也一样。这一段改不了 |
| 飞书多维表格 **读**一次（listRecords） | 中位 **979 ms** | 国内直连实测；服务端到飞书更快，线上 `feishuRoundTripMs` 约 280~400 ms |
| 飞书多维表格 **写**一次（batch_create / batch_update / batch_delete） | 中位 **2492 ~ 3715 ms** | **写比读慢 2.5~3.8 倍**，这是飞书 API 本身的速度 |

把这三项叠起来，一次「点确认」原本要 3~4 秒。
所以优化的方向只有两个：**少发请求**，以及**别让人等**。

### 已做的六处优化

| # | 问题 | 做法 | 实测效果 |
| --- | --- | --- | --- |
| 1 | 6 张表的数据**一张一张**串行拉 | 改成并行拉 | 串行 6144ms → 并行 **1409ms**（4.4 倍） |
| 2 | 并发时每张表各调一次 `listTables` | 合并成一次，加并发锁共用同一个 Promise | 省掉约 0.6 秒 |
| 3 | 写库时逐张表**排队**等 | 改成**表间并行、表内串行** | 两表 2450ms → **1242ms** |
| 4 | 容器被回收后第一个访问的人干等 | 启动即**预热**（`loadAll(true)`） | 冷启动 6700ms → **约 2000ms**，且打开页面时往往已备好 |
| 5 | 一次动作发**两个**写请求（`Rules.nextCodes` 先占编码、主事务再落库） | 前端把同一个动作里的多个写合并成一个请求 | 入库/确认到货：**2 个请求 → 1 个**，少一次网关往返（约 550ms）+ 少一次飞书写 |
| 6 | 界面**干等**飞书写完（3~4 秒） | 写入改成「本地立即生效 + 后台提交」 | 确认按钮**约 1ms 返回**（原来 3~4 秒） |

**为什么"表间可以并行、表内不行"**：飞书的写冲突（`1254291`）是针对**同一张表**的。
实测同时写两张不同的表不会冲突，耗时与只写一张相当（1242ms）；
而同一张表内并发写才是官方明确会出问题的场景，所以表内一律排队。

**预热为什么不会重复加载**：`loadAll` 内部用同一个 `STATE.loading` Promise 去重，
预热和第一个真实请求会共用同一次加载，不会各拉一遍。

### 第 6 项：为什么可以不等，以及「可追溯」怎么保住

数据层在内存里本来就有一份完整镜像，界面渲染读的就是它。
写操作先在镜像上演算完，界面要的数据就已经齐了——**等的那几秒纯粹是在等飞书**。

所以 `runTx` 在镜像上算完就返回，变更进一个队列，由后台提交：

- **合并**：同一个动作里的多次 `runTx`（比如"先占编码、再落库"）在 120ms 的窗口内
  被合成**一个** `/api/write`。窗口有 800ms 上限，改动不会一直悬在本地。
- **如实交代**：左下角有个小角标，写的时候显示「同步中 · N 项」，
  写完了显示「已同步到飞书」再淡出。**写失败会变红并写明原因**，
  同时自动从服务器重拉一份、重新画界面——界面显示的永远是服务器上真实存在的数据。
- **不会装作成功**：失败时还会弹一条明确的错误提示，并且丢掉队列里还没发的改动
  （它们是建立在失败那一批之上的，比如已经占掉的编码）。
- **不会丢**：写请求带 `keepalive`，点完确认立刻关页面/切走，请求照样发得出去；
  页面切到后台时也会先把待发队列冲出去。
- **不会互相冲掉**：只要本地还有没落库的改动，「切回页面自动对齐」就不会去重拉数据
  ——否则会把队友（其实是你自己）刚登记的东西从界面上抹掉。

**大事务仍然等确认**：导入备份、清空数据这类操作（带 `clear` 的、或一次超过 300 条 op 的）
走的是老路径，失败了要当场知道，不能后台悄悄做。

> 写入本身一点没变：照样进多维表格、照样带操作人和时间戳。
> 变的只是**界面不再干等**，并且多了一个如实反映同步状态的角标。
> 想退回「等服务器确认才返回」的老行为，在 `feishu.config.json` 里加
> `"strictWrites": true` 即可。

### 线上自查

```bash
curl https://fever-inventory.app.workbuddy.host/api/health?probe=1
```

看这几个字段：

- `prewarmMs` —— 启动时预热花了多久（正常 2000ms 上下）；
- `dataLoaded` —— 数据是否已在内存。**如果是 `false`，说明容器刚被回收**，
  这时第一个操作的人要等整个加载过程；
- `feishuRoundTripMs` —— 本服务到飞书的**读**往返耗时（注意不是写）。

> 托管平台会把**闲置的容器回收**，所以隔一段时间再用就是一次冷启动。
> 这不是故障，预热就是为了让这段等待和平台自身的启动流程重叠掉。

### 还可以继续压榨吗

- **服务端每次写都深拷贝整个镜像**（`applyOps` 里的 `JSON.parse(JSON.stringify(mirror))`）。
  24 条记录时是 0.04ms，可以忽略；等「出入库流水」涨到几千条以后会成为几十毫秒的量级。
  到那时改成「只拷贝这次会改到的表」即可，现在不值得动。
- **`/api/data` 每次返回全量数据**。同理，记录多到几 MB 时需要改成增量同步。
  战队规模（千级记录、几百 KB）下暂时没必要。
- 网关那 550ms 和飞书写入的 2~4 秒都是平台与飞书的固有成本，服务端改不动。

## 排错：队员打开应用报「登录状态已失效」

这个报错来自 `/api/*` 返回的 401，含义是**服务端认不出请求里的会话令牌**。
按下面两条排查，基本能覆盖全部情况。

### 1. 请求被网关注入了自己的 Authorization（线上环境的真实原因）

托管平台的网关（腾讯 STGW / EdgeOne）会给**每个请求**塞一个它自己的
`Authorization`（形如 `Bearer eyJhbGciOiJIUzI1N...` 的 JWT），
把前端发的 `Authorization: Bearer <队员令牌>` **整个覆盖掉**。
于是服务端拿着网关的令牌去校验，永远失败。

**所以令牌不能只靠 `Authorization` 传。** 现在的做法是：

- 前端同时带 `X-Session-Token`（自定义头，网关不动它）和 `Authorization`；
- 服务端把两个头都当作候选，**逐个校验，谁通过认谁**（`candidateTokens`）；
- 两个都不对才 401 —— 伪造的令牌不会因为"多试一个头"而被放过。

这一点有回归测试固定住：`test-e2e.js` 里有两条断言，一条要求
"Authorization 被覆盖时仍能靠 X-Session-Token 认出身份"，
另一条要求"只有网关令牌时仍然被拒"。

### 2. 服务端重新部署过（令牌本身没问题）

会话令牌是**自签名**的（`lib/session.js`）：载荷里放 openId/姓名/过期时间，
用 `appSecret` 派生出的密钥签名，校验只靠算签名、不需要记住任何东西。

用"发随机串存在内存 Map 里"的常见写法时，每次重新部署都会把所有在线的人踢下线。
改成自签名之后，重新部署、进程重启、换实例都不影响已发出的令牌，
队员不会掉线。

另外前端有一层兜底：数据层收到 401 会**自动重新免登一次再重试**，
重登也失败才把错误抛到界面上（`db-remote.js` 的 `renewToken` + `feishu-auth.js` 的 `renew`）。

### 3. 前端发请求时必须带令牌（登录层踩过一次的坑）

`/api/me` 的用途就是"本地缓存的令牌还有效吗"。如果登录层发这个请求时**不带令牌**，
它必然 401，于是每次打开应用都会：白跑一个必定失败的请求 → 丢掉明明有效的令牌
→ 退回一次完整的飞书免登（队员感觉"怎么又要授权一遍"）。

这个坑**只有线上才看得见**（登录层只在飞书客户端里跑），是靠线上日志
`[会话] 拒绝 POST /api/me —— 带了的 1 个令牌都校验不通过` 定位的：
"带了 1 个令牌"指的是网关注入的那个，"校验不通过"指的不是队员的令牌。

现在 `feishu-auth.js` 的 `postJson` 会在 `state.token` 存在时同时带
`X-Session-Token` 和 `Authorization`。**这一段不能删**，
`npm run test:feishu-auth` 的用例 [1] 就是钉住它的
（把这段摘掉会有 3 项转红）。

> 密钥没配 `sessionSecret` 时由 `appSecret` 派生。**换 appSecret 会让所有人重新登录一次**，
> 这是符合预期的。

## 排错：左下角显示「同步失败」

界面不再等飞书写完，所以必须有个地方交代后台的成败 —— 就是左下角那个小角标。
它出现红色「同步失败」时，含义是：**刚才那次点击没有被写进多维表格**。

此时系统已经自动做完三件事，不需要额外操作：

1. 从服务器重新拉了全量数据（界面已经回到真实状态，刚才那次点击相当于没发生）；
2. 弹了一条写明原因的提示；
3. 把队列里还没发出去的改动一并丢掉（它们建立在失败那一批之上）。

把鼠标停在红色角标上能看到完整原因，点一下可以关掉。常见原因有两类：

- **编号已被占用**：同一瞬间有别人也在登记同一批编号。重新操作一次即可
  （数据已经刷新过，这次会拿到新的可用编号）；
- **网络或飞书抖动**：服务端对可重试的错误（写冲突 `1254291`、频率限制 `1254290`）
  已经自动退避重试最多 5 次，重试都失败才会报到这里。稍后重试即可。

如果每次都失败、且原因固定（比如权限、字段名不匹配），那是配置问题，
用 `npm run check` 看飞书原样返回的 `permission_violations`。

> 想临时确认「现在界面上的数据和服务器是不是一致」：在控制台执行
> `FEVER.DB.pendingOps()` —— 返回 `0` 就表示没有未落库的改动。

## 接口

除 `/api/login` 外都需要会话令牌，放在 `X-Session-Token` 头里
（`Authorization: Bearer <session>` 也认，但线上会被网关覆盖，别依赖它）。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/health` | 健康检查。带 `?probe=1` 时顺便量一次到飞书的往返耗时 |
| POST | `/api/login` | 入参 `{code}`，出参 `{token, user:{openId,name,avatarUrl}}` |
| GET | `/api/me` | 校验 session 是否还有效 |
| GET | `/api/data` | 一次拉全部表 + 各表下一个可用编号 |
| POST | `/api/write` | 入参 `{ops:[…]}`，一个请求内按顺序执行整批变更 |
| GET | `/` 及静态路径 | 伺服 `public/` 里的前端 |

`ops` 的四种形式：`add` / `put` / `delete` / `clear`，与前端 `runTx` 里收集到的操作一一对应。
一个请求里可以带多个事务的操作 —— 前端会把同一个动作里的多次 `runTx`
（比如"先占编码、再落库"）合并成一个请求发过来，按顺序执行。

## 管理员与权限

采购申请的**审批**（同意 / 驳回）只有管理员能做，**兵种预算额度**也只有管理员能改。

### 谁是管理员

`config.json` 的 `admins` 数组，写姓名或 openId 都行，**任一匹配即算管理员**
（比对时去掉首尾空格、忽略大小写）：

```json
{
  "appId": "cli_xxx",
  "appSecret": "xxx",
  "admins": ["张三", "ou_xxxxxxxxxxxxxxxx"]
}
```

身份来自飞书的登录链路（`/api/login` 或 `/api/me`），**队员改不了** ——
页面上的姓名就是飞书给的。启动日志会把识别到的管理员名单打出来，方便核对。

### 两道闸

| 层 | 作用 | 能不能绕过 |
| --- | --- | --- |
| 前端 `DB.isAdmin()` | 只决定**按钮画不画**（离线版恒为 true） | 能，改前端即可 |
| 服务端 `applyOps` 里的 `adminOnlyReason()` | **真正拒绝**：返回 `err.forbidden = true`，HTTP 403，且整个请求零写入 | 不能 |

服务端拦两类东西：

- `ADMIN_ONLY_FIELDS`：`purchaseRequests` 的 `approval`（审批状态）；
- `ADMIN_ONLY_SETTINGS`：`budgetByTroop`（兵种预算额度）。

**只拦"真的改了值"的写入**：值没变的 `put` 放过 —— 否则队员只是编辑一下申请备注，
也会连带把没动过的 `approval` 字段一起提交上来，被判成越权。

### 删除为什么不限权限

物品身份 / 采购申请 / 发票 / 出入库流水**谁都能删**（离线版只有一个人，飞书版如实记录操作人）。
守住的底线不是"谁能删"，而是**删了一定留痕**：每删一条都会往
`settings.deleteLog` 里追加一笔（时间、操作人、对象、删除当时的完整快照），
并随备份一起走。详见 PRD 第 15.5 节。

## 两个关键设计

### 1. 写请求整体串行，但表与表之间并行

多维表格**没有事务、也没有自增锁**，官方明确不建议对同一张表并发读写
（会返回 `1254291 Write conflict`）。所以：

- **请求级**：一条队列把所有写请求排成队，前一个处理完才轮到下一个；
- **表级**：一个请求内部涉及的多张表**并行**写（实测不冲突，省一半时间）；
- **表内**：同一张表内的删 / 增 / 改**严格串行**，这是飞书会冲突的地方。

这样既保住了"不会写冲突"，又不会让多表操作白等。

### 2. 自增编号：客户端先占号，服务端校验

`purchaseRequests / invoices / transactions` 三张表的主键是自增数字。
多维表格的 record_id 不能自定义，也没有自增能力，所以编号由前端在本地先占一个
（从 `/api/data` 返回的 `sequences` 起算），服务端在写入前校验有没有被占用：

- 没被占用 → 直接落库，编号连续、好看；
- 被占用（同一瞬间有别人也在登记）→ **整批拒绝**，返回 409，
  前端会自动重新拉一份数据，提示重新提交。

之所以不做"服务端悄悄换个号"，是因为一次操作里常常一张票带着好几条记录
（比如入库是"发票 + 物品 + 流水"一起写），换号会让它们之间的引用指错。

---

## 并发与失败处理

- 落库过程中任何一步失败，内存镜像都会重新从多维表格拉一遍对齐
  （多维表格没有事务，可能已经写了一半，重拉才是准的）；
- 网络抖动、频率限制、写冲突（`1254290 / 1254291 / 1254607 / 1255040`）会自动退避重试；
- 授权码过期、用户无权限这类错误不会重试，直接把可读的中文原因返回给界面。

---

## 假定单实例运行

**服务一启动就会预热**：端口可用后立刻把全部数据拉进内存做镜像，之后读写都基于这份镜像 + 写回多维表格。
（预热失败不影响使用，第一个真实请求会重试，且两者共用同一次加载。）

**当前托管环境是单实例，所以这份镜像总是最新的。**
如果以后要多实例横向扩展，需要把镜像换成"每次直读多维表格"，或加一层共享缓存。

> 注意：这条限制**只针对数据镜像**。会话令牌是自签名的，不受单实例假设影响 ——
> 换实例或重启都不会让队员掉线。

## 部署

`server/` 目录本身就是完整的可发布单元（含 `public/` 里的前端）。
前端产物由根目录的 `npm run build:feishu` 生成并自动同步到 `server/public/`。

发布前确认两件事：

1. `server/config.json` 里 `appId` / `appSecret` / `bitableAppToken` 都齐了；
2. `server/config.json` **没有被提交到公开仓库**（已在 `.gitignore` 里）。

平台会通过 `PORT` 环境变量注入端口，`npm start` 即可。

> 发布工具用的是固定排除清单（`node_modules` / `.git` / build 输出），
> **不读 `.gitignore`** —— 所以 `config.json` 和 `public/` 会正常随包上传。
> 这一点是反推出来的：该工具会用 `.env*` 里的连接串判断项目是否依赖数据库，
> 而 `.env` 通常都被 gitignore，说明排除逻辑与 gitignore 无关。

**当前线上地址**：`https://fever-inventory.app.workbuddy.host/`
界面与接口同域，`feishu.config.json` 里的 `apiBase` 留空即可。
